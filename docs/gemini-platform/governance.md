# Доступ, HITL, безопасность и соответствие требованиям

---

## 1. Классы данных и контуры

| Класс данных | Что входит | Ранг |
|---|---|---|
| `private_development` | сценарии, budget notes, внутренние монтажи | 3 |
| `restricted_production` | call sheets, назначения группы, планы локаций | 2 |
| `partner_shared` | одобренные материалы, отобранные дэйлисы, технические метаданные | 1 |
| `public_fan_safe` | только опубликованные материалы и безопасные summaries | 0 |

| Контур | Потолок | Кто |
|---|---|---|
| `internal` | 3 | режиссёр, сценарист, линейный продюсер, группа |
| `partner` | 1 | подрядчики, пост-продакшн, партнёрские callbacks |
| `fan` | 0 | fan-facing ассистент, маркетинговые поверхности |

Контур читает свой ранг и всё, что ниже. Правило проверяется в трёх независимых
точках:

1. **Старт workflow** — внутренний workflow не запускается из fan-контура
   вообще; прогон завершается `BLOCKED` до первого узла, retrieval не
   происходит.
2. **Retrieval** — документ выше потолка не попадает в контекст промпта.
   Отфильтрованные документы записываются как `denied_reads`.
3. **Governance-агент** — повторно проверяет **каждую цитату**, попавшую в
   вывод, независимо от фильтра, который её пропустил.

Различие, которое легко потерять:

- **`denied_reads`** (отказ в чтении) — штатный трафик. Фанат спрашивает про
  фильм, корпус содержит сценарий, сценарий отфильтрован. Это система, которая
  работает правильно; блокировать прогон нельзя, иначе fan-контур не работает
  вовсе. Логируется как issue уровня `low`.
- **`violations`** (утечка) — данные выше потолка **дошли до вывода**. Всегда
  критично и всегда блокирует прогон. По построению этого не должно случаться —
  проверка существует как defence in depth на случай ошибки в фильтре.

Классификация — метаданные, которые ставит человек, а не результат вывода во
время запроса. Манифест корпуса (`corpus.example.json`) отвергает документ с
неизвестным классом: подстановка значения по умолчанию — ровно тот отказ,
против которого классификация и вводится.

## 2. HITL-матрица

| Действие | Нужен человек | Почему |
|---|---|---|
| `draft_artifact` | нет | черновик ничего не меняет |
| `internal_notify` | нет | уведомление группе обратимо |
| `schedule_commit` | **да** | ошибка в плане стоит съёмочного дня |
| `call_sheet_publish` | **да** | call sheet — обязательство перед группой |
| `asset_publish` | **да** | публикация необратима |
| `fan_release` | **да** | риск спойлера и утечки материалов |
| `legal_sensitive` | **да** | юридические последствия |
| `budget_affecting` | **да** | финансовые обязательства |
| `partner_write` | **да** | мутирующий вызов на стороне партнёра |

Гейт по умолчанию **останавливает**: действие исполняется автоматически только
если его явно нет в обязательном списке. Обратная логика (по умолчанию
разрешено, запрет перечислением) недопустима — новый тип действия окажется
разрешённым по умолчанию.

Запрос на утверждение содержит варианты, риски и цитаты, чтобы решение
принималось без возврата в переписку. Решение атрибутируется (`approver_id`),
отказ терминален, выбор непредложенного варианта отвергается.

## 3. Безопасность

| Поверхность | Мера |
|---|---|
| Вход | LB + IAP / Identity Platform, Cloud Armor, закрытый прямой `run.app` endpoint |
| Агент → MCP | Agent Gateway + Agent Registry + Agent Identity, allow-list инструментов |
| Промпты и вывод | Model Armor: prompt injection, утечки данных, вредный вывод |
| Секреты | Secret Manager; ключ подписи webhook ротируется отдельно от токенов |
| Права | least privilege, отдельные permission boundaries на агента |
| Аудит | Cloud Audit Logs + Data Access logs + audit trail прогонов |

Отдельный вектор для медиа: **prompt injection через контент**. Сценарии,
комментарии в ревью и ответы партнёрских инструментов — это внешний текст,
который агент читает. Меры: инструменты по allow-list, вывод модели
валидируется структурно перед записью в состояние, а действия с последствиями
проходят HITL — модель не может «уговорить» систему опубликовать материал,
потому что публикация вообще не находится в её власти.

## 4. GDPR и правовые ограничения

Юрисдикции в исходном ТЗ не уточнены, поэтому базовый режим — GDPR-ready:
минимизация данных, consent-first для голоса и биометрии, ограничения хранения
и рабочий процесс удаления.

Что нужно зафиксировать до production:

- **Data residency.** По данным ТЗ, RAG Engine поддерживает VPC-SC и CMEK, но не
  поддерживает контроль резидентности данных. Если в материалах есть
  персональные данные с жёсткими требованиями к резидентности — либо не класть
  их в этот слой, либо держать отдельные корпуса без чувствительного
  содержимого. Пункт требует проверки у вендора перед развёртыванием.
- **Биометрия.** Голосовые клоны, face embeddings и идентификация актёров
  попадают под особые категории данных (Art. 9 GDPR). Позиция по умолчанию:
  никакого voice cloning и идентификации по лицу без отдельного правового
  основания, договора и модели согласия. Технически платформа должна нести
  consent-флаги, redaction, лимиты хранения и процедуры удаления.
- **Union rules и договоры с актёрами** — отдельный legal workstream; технически
  выражаются как ограничения планировщика (`unionHours`) и как политика.

Redaction (`Redactor`) — последняя линия обороны, а не контроль доступа:
документ, не прошедший политику, отбрасывается целиком и до redaction не
доходит. Redaction снимает контакты и финансовые реквизиты из текста, который
покидает внутренний контур.

## 5. Риски и меры

| Риск | Почему важно | Мера |
|---|---|---|
| Неустойчивая или частичная реализация MCP у партнёра | самый вероятный стоп-фактор интеграции | contract-first профиль, адаптер на Cloud Run, контрактные тесты, деградация на локальную эвристику |
| Prompt injection через документы и комментарии | приватные материалы и ассеты | Model Armor, allow-list инструментов, структурная валидация вывода, HITL |
| Разрастание прав доступа | контуры легко смешиваются | раздельные хранилища, проверка контура в трёх точках, `denied_reads` в отчёте |
| Стоимость уходит в search/grounding/live | недооценённый финансовый риск | budget guard с alert до потолка, автодаунгрейд tier, кэширование, квоты на live |
| Ошибки в расписании и автономность | ошибка call sheet стоит съёмочного дня | HITL на publish/commit, детерминированные проверки, ранжирование с рисками |
| Голос и лицо | high-risk legal area | consent registry, минимизация, отсутствие идентификации по умолчанию |
| Эволюция вендорских API | терминология и функции быстро меняются | abstraction layer, контрактные тесты, ADR, ежеквартальный обзор платформы |
| Region / SaaS outage | on-set процессы чувствительны ко времени | async fallback, экспортируемые артефакты, ручной обходной путь, второй регион |
