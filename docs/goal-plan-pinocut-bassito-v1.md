# Goal Plan: PinoCut + Bassito

Дата: 2026-07-04
Режим: goal-driven — от главной цели к измеримым этапам.
Контекст: рынок массово продаёт «AI-клипперы» (Vizard, Opus Clip, VEED). PinoCut закладывался глубже — как агентный production pipeline. Этот план фиксирует, как превратить преимущество в глубине в работающий продукт.

---

## 1. Позиционирование: где мы и где рынок

| | Клипперы (Vizard / Opus Clip / VEED) | PinoCut + Bassito |
|---|---|---|
| Задача | Длинное видео → вирусные шортсы | Сырой материал → собранная профессиональная сцена/ролик |
| Анализ | Хайлайты, транскрипт, virality score | Семантика сцены (Romeo FV): scene goal, mood, continuity |
| Монтаж | Авто-субтитры + зум + B-roll | Шаблоны сцен (dialogue / montage / trailer), rubric-отбор дублей, bounded tool API |
| Генерация | Нет (только нарезка исходника) | Bassito: bridge shots, extend, restyle недостающего материала |
| Оркестрация | Монолитный сервис | LangGraph + роли (Romeo — режиссёр, Andrew — контроль качества, Bassito — исполнитель) |
| Кому | Контент-креаторы, SMM | Продакшн из генеративного/сырого футажа, AI-фильммейкинг |

**Позиция:** не конкурировать с клипперами за «нарезать подкаст на шортсы». Ниша — **Scene Stitcher / агентная сборка сцен**: пользователь даёт цель сцены, стиль и клипы (в т.ч. сгенерированные), система собирает готовую сцену и сама догенерирует недостающие кадры. Этого у клипперов нет ни у одного.

---

## 2. Честный аудит текущего состояния

Что **реально работает**:
- Основной 6-стадийный пайплайн (`pinocut/agent.py`, `stages/`) — реальный рендер через moviepy/FFmpeg, ducking, LUT, lower thirds.
- Scene Stitcher (`scene_stitcher.py`) — детерминированный планировщик: отбор, трим, таймлайн, экспорт timeline JSON и SceneOps snapshot.
- Dispatch SceneOps в RomeoFlexVision через GitHub Actions.

Что **заглушки / упрощения** (главные разрывы):
1. **Scene build не рендерит видео.** `SceneToolbox.render_preview` и `export_scene` пишут JSON-манифесты, а не mp4 (`scene_tools.py:171-195`). Полный рендер-пайплайн существует рядом, но не подключён к сценам.
2. **Bassito не существует как исполнитель.** `request_extend` / `request_restyle` / `request_bridge_shot` возвращают dict `{"status": "queued"}` (`scene_tools.py:205-213`). Задачи ставятся в очередь, но никто их не выполняет, regeneration loop не замыкается.
3. **«Семантический анализ» — совпадение токенов.** `_calculate_scene_overlap` сравнивает слова из scene goal с именем файла и метаданными (`scene_stitcher.py:659`). Метаданные при probe пустые (`{}`), поэтому `quality_score`/`shake_score` берут дефолты — рубрика Andrew фактически оценивает только разрешение и длительность.
4. **Субтитры пустые.** `generate_subtitles` возвращает `[]` (`scene_tools.py:164`), хотя в основном пайплайне Whisper/VAD уже есть.
5. Два пайплайна (agent.py и scene_stitcher.py) не разделяют код анализа и рендера.

## 3. Главная цель (Goal)

> **За один вызов `pinocut scene build` из папки клипов получается отрендеренная mp4-сцена, где отбор дублей основан на реальном анализе контента, а недостающий материал догенерирован Bassito автоматически.**

### Критерии успеха (Definition of Done для v1.1)
- [ ] `pinocut scene build ./clips --goal "..."` выдаёт `scene_XX.mp4` + timeline JSON + SceneOps snapshot — без ручного монтажа.
- [ ] Andrew-скоринг использует реальные сигналы (Whisper/VAD, гистограммы, shake, Romeo FV), а не имя файла; на тестовом наборе отбор совпадает с ручным выбором редактора ≥ 70%.
- [ ] Bassito-джобы исполняются реальным бэкендом: хотя бы один провайдер генерации + локальный ffmpeg-фоллбэк; regeneration loop пересобирает сцену после готовности джобов.
- [ ] Демо: 8–10 сырых клипов → 35-секундная сцена «cinematic dark sci-fi» с bridge shot — публичное видео для позиционирования.

## 4. Этапы (goal → subgoals)

### G1. Реальный рендер сцены — «сцена = mp4, не JSON»
Приоритет: **P0**, это блокер всего остального.

- **G1.1** Вынести рендер из `stages/render.py` в переиспользуемый `RenderService` (moviepy + ffmpeg-режимы), принимающий `TimelineV1`.
- **G1.2** `SceneToolbox.export_scene` → реальный рендер: трим по `source_in/out`, переходы (`cut`, `crossfade`), reflow-оверлапы.
- **G1.3** `render_preview` → низкорезный быстрый прокси (480p, ultrafast preset) для итераций Romeo.
- **G1.4** Аудио: применить существующий ducking из `AudioMixStage` к `TimelineAudioSegment` (music + voiceover, target LUFS −14).
- **G1.5** Тест: e2e-фикстура из 3 синтетических клипов (ffmpeg color/testsrc) → проверка длительности, порядка сегментов, наличия аудиодорожки.

**Выход:** scene build выдаёт mp4. Критерий: длительность рендера в пределах ±0.5с от `actual_duration_sec` таймлайна.

### G2. Bassito как реальный исполнитель — «очередь, которая исполняется»
Приоритет: **P0** для дифференциации (это фича, которой нет у клипперов).

- **G2.1** `BassitoJob` как модель в `state.py`: `job_id`, `job_type`, `status` (queued → running → done/failed), `source_clip_id`, `prompt`, `artifact_path`, `cost_estimate`.
- **G2.2** `BassitoRunner` с адаптерами бэкендов:
  - `FfmpegBackend` (локальный фоллбэк): extend = slow-mo/loop last seconds, restyle = LUT/стабилизация из `effects.py`, bridge = Ken Burns по стоп-кадру;
  - `GenerativeBackend` (интерфейс) — первый провайдер: Higgsfield / Runway / Kling API (extend, restyle, text-to-video bridge). Асинхронно, с retry и cost-логом.
- **G2.3** Замкнуть **regeneration loop**: `scene build --wait-bassito` — после done-джобов артефакты попадают в `available_clips`, сцена пересобирается (`timeline_version + 1`), `queueState` проходит `waiting_bassito → completed`.
- **G2.4** Бюджетные ограничения: max джобов на сцену, max стоимость, политика «ffmpeg-фоллбэк, если генерация дороже X».
- **G2.5** Reframing из `calculate_dynamic_reframing` реально применять при рендере (сейчас только пишется в metadata).

**Выход:** сцена с недостающим материалом достраивается сама. Критерий: демо-сцена с ≥1 сгенерированным bridge shot, собранная без ручных шагов.

### G3. Настоящий анализ — «Romeo видит, а не читает имя файла»
Приоритет: **P1**.

- **G3.1** Переиспользовать `AnalyzeStage` в scene-пайплайне: Whisper/VAD-сегменты речи, keyframe-гистограммы, shake-метрика → заполнять `clip.metadata` реальными `quality_score`, `brightness_variance`, `shake_score`, `action_peak_sec` (сейчас smart_trim работает только если эти поля кто-то положил).
- **G3.2** Romeo FV enrichment для сцен: `scene_description`, `subjects`, `mood`, `location_tag` из `integrations/romeo_vision.py` (HTTP + cache уже есть) — вместо токенов из имени файла в `_calculate_scene_overlap`.
- **G3.3** Семантическое сходство scene goal ↔ клип: embedding-сравнение (локальная модель или LiteLLM), токен-оверлап оставить как офлайн-фоллбэк.
- **G3.4** Субтитры: `generate_subtitles` через Whisper (extra уже объявлен в pyproject), burn-in стилем из `effects.py`.
- **G3.5** Валидационный набор: 20–30 клипов с ручной разметкой «взял бы редактор» → метрика совпадения отбора (цель ≥ 70%).

**Выход:** рубрика Andrew и выбор Romeo обоснованы контентом. Это главный аргумент «глубины» в позиционировании.

### G4. Многосценовая сборка — «из сцен — ролик» (то, чего нет у клипперов)
Приоритет: **P2**, после G1–G3.

- **G4.1** `ProjectState`: упорядоченный список `SceneState` + сквозной `style_profile`.
- **G4.2** Continuity между сценами: Andrew проверяет стыки (свет/локация/mood последнего и первого кадра), Romeo выбирает межсценовые переходы.
- **G4.3** `pinocut project build project.yaml` — сцены описаны декларативно, сборка сцен параллельно, финальный concat + общий саундтрек с ducking.
- **G4.4** Style memory через Moltis: выбранные LUT/pace/transition policy первой сцены наследуются дальше.

### G5. Позиционирование и продукт
Приоритет: **P1**, параллельно с G2–G3.

- **G5.1** Демо-кейс: «8 сгенерированных клипов → готовая сцена за 3 минуты» — видео + пост (прямой ответ тренду из поста про Vizard/Opus Clip: они режут существующее, мы собираем и достраиваем).
- **G5.2** README/лендинг: сравнительная таблица из раздела 1, честная — «мы не клиппер, мы scene assembly agent».
- **G5.3** SceneOps dashboard в RomeoFlexVision довести до review-цикла: HITL-кнопки approve/modify уже заложены в snapshot (`hitlDecision`) — подключить обратный канал (пока можно через repository_dispatch).
- **G5.4** Опционально: тонкий «клиппер-режим» (trailer_cut template + 9:16 reframe + burn-in субтитры) как воронка — знакомый рынку вход, за которым видна глубина.

## 5. Порядок работ (спринты)

| Спринт | Содержание | Результат |
|---|---|---|
| **S1** | G1 целиком + G3.1 | scene build → реальный mp4 с реальными метриками клипов |
| **S2** | G2.1–G2.3 (Bassito runner: ffmpeg-фоллбэк + первый генеративный бэкенд, loop) | сцена достраивает себя; демо-материал для G5.1 |
| **S3** | G3.2–G3.5 + G5.1–G5.2 | vision-обоснованный отбор + публичное демо и позиционирование |
| **S4** | G2.4–G2.5, G3.4, G5.3 | бюджеты, reframing в рендере, субтитры, HITL-цикл |
| **S5** | G4 | multi-scene: из сцен — ролик |

Правило приоритета при конфликте: **сначала то, что сокращает разрыв «обещано в README ↔ работает в коде»** (G1, G2), затем то, что усиливает дифференциацию (G3, G4), затем маркетинг (G5) — но демо (G5.1) делается сразу, как только S2 даёт материал.

## 6. Риски

| Риск | Митигция |
|---|---|
| Стоимость/латентность генеративных бэкендов Bassito | ffmpeg-фоллбэк всегда доступен; бюджеты и cost-gate (G2.4); прокси-превью до финального рендера |
| moviepy медленный на длинных сценах | ffmpeg-режим рендера уже есть в `RenderStage` — сделать его основным для сцен |
| Romeo FV API недоступен / не задеплоен | все vision-зависимые шаги имеют детерминированный фоллбэк (текущие эвристики остаются как degraded mode) |
| Расползание на два пайплайна | G1.1: единый RenderService; далее agent.py постепенно мигрирует на TimelineV1 как общий контракт |
| Рынок клипперов съедает внимание | не воевать за их нишу; демо и messaging только про сборку сцен из генеративного футажа (G5) |
